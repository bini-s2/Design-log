## HTML 기초 — 시맨틱 구조와 폼 요소 학습

`Frontend Study` · `HTML` · `UX/UI` · `Accessibility`

프로덕트 디자인과 프론트엔드 협업에 필요한 HTML 기초 구조를 학습하고, 간단한 예제를 직접 작성했다.

### 학습 내용
- HTML이 화면의 구조와 의미를 정의하고 CSS가 크기·색상·간격 등 시각적 표현을 담당한다는 역할 구분
- `main`, `section`, `article`, `h1`~`h3`, `p` 등 시맨틱 태그를 활용한 정보 구조 작성
- 페이지 이동에는 `a`, 현재 화면의 동작 실행에는 `button`을 사용하는 기준
- `href`, `class`, `type`, `id`, `for` 등 HTML 속성의 기본 역할
- `label`과 `input`을 `for`·`id`로 연결하는 방법
- 검색·이메일·일반 텍스트 등 입력 목적에 맞는 `input type` 구분
- `form`과 `button type="submit"`을 이용해 입력과 제출을 하나의 기능으로 구성

### 협업 관점
- 디자인 레이어명을 모양보다 `Page Title`, `Section Title`, `Save Button`처럼 역할 중심으로 지정하면 구현 구조를 전달하기 쉽다.
- 입력창 설계 시 라벨과 플레이스홀더의 역할을 구분하고 기본·포커스·오류·비활성 등 상태를 함께 정의해야 한다.
- HTML 태그와 속성은 영단어 자체를 암기하기보다 반복되는 역할과 연결 구조를 중심으로 익힌다.

### 정리

화면의 시각적 형태뿐 아니라 요소의 의미와 동작을 구분해 HTML 구조로 옮기는 기초를 익혔다. 링크·버튼과 입력 요소의 역할을 구분하고, 접근성과 개발 협업에 필요한 구조를 직접 작성했다.


## 일본어 소리 검색 — 문장 복원·후보 신뢰도 체계화

`Search UX` · `Japanese Learning` · `Ranking` · `QA`

실제 검색 테스트에서 반복적으로 발생한 오류 유형을 모아, 개별 예시를 수정하는 방식에서 벗어나 검색 구조와 검증 기준을 전반적으로 정리했다.

### 문제 유형 정리
- 사전 표제어 중심 검색으로 인해 활용형·회화 축약형·가사·문학적 문장을 놓치는 문제
- IME가 발음만 비슷한 부자연스러운 한자·가나 조합을 만드는 문제
- 잘못 복원된 일본어도 번역기가 한국어로 번역하면 후보로 살아남는 문제
- Google 자동완성에서 표현 뒤에 인명·가수명·가사·의미 같은 검색 맥락이 붙는 문제
- 실제로 많이 검색되는 자연스러운 표현보다 희귀 사전 항목이 높은 점수로 올라오는 문제
- 정확도를 높이기 위해 자동완성 일치 조건을 과도하게 강화하면서 자연스러운 문장까지 누락되는 문제

### 개선 내용
- 후보마다 신뢰도 계층을 두고 제어 표현, 실제 검색 보조, 외래어 검증, 문법 검증, 사전 검색의 우선순위를 분리했다.
- Google 자동완성 노출 순서를 검색 인기도의 보조 신호로 사용해, 발음 점수가 비슷하면 실제로 많이 검색되는 표현을 먼저 보여주도록 랭킹을 조정했다.
- 자동완성은 후보 생성기가 아니라 검증 신호로 제한하고, 입력 소리와 무관하게 뒤에 붙은 검색 확장 문구는 제거했다.
- 상위 IME 변환, 발음 일치도, 일본어 조사·활용·축약·종결 표현을 함께 보는 문장 구조 점수를 추가했다.
- 자동완성에 없더라도 회화 축약형과 활용형, 명사로 끝나는 문학적 구절 등은 문법 구조가 충분하면 후보로 복원할 수 있도록 확장했다.
- 일본어 표기와 히라가나 읽기를 각각 번역한 결과가 크게 어긋나는 경우 후보를 제외해 번역기 기반 오역을 줄였다.
- 검증된 Google·문장·외래어 후보가 있으면 같은 발음권의 희귀 사전 항목과 낮은 신뢰도의 IME 후보를 제거하도록 후처리 규칙을 통합했다.
- 지금까지 문제가 됐던 대표 검색 유형을 회귀 테스트 대상으로 묶고, 검색 품질 정책이 사라지거나 깨질 경우 배포 단계에서 확인할 수 있는 테스트를 추가했다.

### 정리

한글로 기억한 일본어를 찾는 기능은 단순한 발음 유사도 검색이 아니라 **발음 복원 → 실제 사용 가능성 → 문법 구조 → 의미 검증 → 검색 인기도 → 후보 신뢰도**를 함께 판단해야 안정적인 결과를 만들 수 있다는 점을 확인했다.

앞으로는 새 오류가 나올 때 해당 표현만 추가하기보다, 어떤 오류 유형에 속하는지 먼저 분류하고 기존 검증 계층에서 재발하지 않도록 수정하는 방식을 유지한다.
