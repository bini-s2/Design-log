# 2026-10-21 — 프로덕트 디자인 협업 프로세스 학습

**분야:** UX/UI / Product Design / Study / Collaboration

## Overview

UX/UI 베이스캠프 마지막 단계에서 프로젝트 시작부터 개발 전달·검수까지의 실무 협업 프로세스를 정리했다. 특히 용어만 알고 있던 Kick-off와 Hand-off를 Design Review 및 QA와 구분해 이해하고, 개인 블로그용 학습 노트 초안으로 정리했다.

## 학습 내용

- **Kick-off:** 프로젝트의 목표, 문제 정의, 대상 사용자, 범위, 일정, 역할, 의사결정 기준을 팀과 맞추는 시작 단계.
- **Design Review:** 시안이 프로젝트 목표와 사용자 문제 해결에 적합한지 검토하고, 판단 근거와 피드백을 공유하는 과정.
- **Hand-off:** 확정된 디자인을 개발팀이 구현할 수 있도록 화면 흐름, 상태, 예외 상황, 반응형 기준, 디자인 스펙을 전달하는 과정.
- **QA:** 실제 구현이 디자인 의도와 사용성 기준에 부합하는지 확인하며 기능·상태·반응형·접근성 등을 점검하는 활동.

## 핸드오프 학습 포인트

- **User Flow:** 사용자가 목표에 도달하기까지 이동하는 화면과 행동의 연결.
- **Use Case / UI State:** 사용 시나리오와 Default·Loading·Empty·Success·Error 등 화면 상태를 구분.
- **Responsive Layout:** 화면 크기별 레이아웃 변화 및 브레이크포인트 정의.
- **Figma 정리:** 페이지·컴포넌트·화면명·상태·기기별 시안을 일관된 규칙으로 관리.

## 정리 결과 및 배운 점

킥오프를 '기획·목표를 맞추는 첫 회의'로, 중간 시안 피드백은 '디자인 리뷰'로, 핸드오프는 '구현 가능한 기준을 전달하는 과정'으로 구분했다. 프로젝트는 Kick-off → 리서치·디자인 → Design Review → Hand-off → 개발 → QA로 설명할 수 있으나 실제 업무에서는 검토·수정·검수가 반복될 수 있다는 점도 정리했다.

블로그 글 초안은 공부 기록에 맞게 자연스러운 설명체로 작성했으며, 복사·붙여넣기 시 표시되는 마크다운 굵게 처리 기호를 사용하지 않는 형식으로 수정했다. 초안 작성까지만 확인되었으며 블로그 발행은 확인되지 않았다.

> 공개 작업 로그 원칙에 따라 개인적인 내용과 확인되지 않은 성과는 제외했다.

## 추가 학습 — 음악 스트리밍 앱 UX 문제 분석과 반응형 설계

**분야:** UX/UI / Product Design / User Research / Figma / Study

### STEP 5 → STEP 6 분석

- 자주 쓰는 음악 스트리밍 앱에서 **곡 하나를 재생목록 A와 B에 저장하기**를 과제로 선정했다.
- 이미 저장한 곡에 대한 중복 안내 후 다른 목록으로 이어서 저장하기 어려워 메뉴 진입을 반복해야 하는 사용 흐름 단절을 분석했다.
- 중복 안내에 '무시하고 추가'가 보일 때와 보이지 않을 때가 있다는 관찰을 기록하고, 원인이나 재현 조건은 확인 전이라고 구분했다.
- User Flow와 Use Case를 구분했다. User Flow는 행동·화면 이동 경로, Use Case는 목표를 달성하는 과정의 다양한 조건과 시스템 반응을 검토하는 방식으로 이해했다.
- 화면 상태 Default, Success, Already Saved 및 사용자 상호작용 상황을 관찰 중심으로 정리했다. UI 상태 명칭과 엄밀한 유즈 케이스 시나리오가 다른 개념이라는 점도 확인했다.

### 동일 Task 레퍼런스 비교

- **Spotify PC:** 하위 메뉴에서 플레이리스트를 선택하고 검색할 수 있으며, 동일 목록에 이미 들어 있는 곡을 추가하려 하면 '그래도 추가하기 / 추가 안 함' 선택형 모달을 제공하는 모습을 직접 확인했다.
- **Melon PC 웹:** 곡의 '담기'에서 플레이리스트 선택 팝업을 열고 새 리스트를 만들 수 있었다. 동일 곡 중복 추가 시 브라우저 Alert로 안내했으며, '확인' 후에도 리스트 선택 팝업이 유지되는 것을 직접 확인했다.
- Toast, 브라우저 Alert, 선택형 Modal의 역할과 인터랙션 차이를 비교했다. Spotify에서 중복 안내 이후 다른 목록으로의 이어지는 동작은 검증 결과로 단정하지 않았다.
- 재생 대기열 중복 설정과 개인 플레이리스트 저장 정책은 서로 다른 기능이므로 혼동하지 않는 원칙을 세웠다.

### 반응형 레이아웃과 개선 가설

- 모바일 하단 탭바와 데스크톱 좌측 사이드바의 내비게이션 구조 차이를 관찰했다.
- HOME의 앨범·재생목록 카드에서 화면 너비 변화에 따라 카드 크기와 열 수를 유동적으로 조정하는 Fluid/Responsive Grid 개념을 학습했다. 화면이 넓어졌다고 모든 요소를 같은 비율로 늘리는 것은 아니라는 점을 구분했다.
- **개선 가설:** 저장 화면에서 기존에 저장된 목록은 '이미 저장됨'으로 알리고, 신규 목록은 체크박스로 여러 개 선택해 한 번에 추가할 수 있도록 한다. 기존 곡 삭제는 이 기능 범위가 아니며, 동일 재생목록 내 중복 추가 허용 여부는 별도 검증 과제로 남겼다.
- 과제 제출용 분석(AS-IS와 사용 환경 검토)과 선택적 개선 제안(TO-BE)을 분리하여 정리했다.

### 학습 마무리

베이스캠프 최종 UX 과제 자료를 정리하고, 실무 협업에 필요한 화면 흐름·상태·반응형 사고를 연습했다. Figma 프로토타입의 개념과 이전 제작 경험을 확인했으며, 캠프에 기대하는 실무 프로젝트·구현·검증 경험을 설문 문장으로 정돈했다. 과제 최종 제출 및 블로그 게시 완료 여부는 별도 확인되지 않았다.
